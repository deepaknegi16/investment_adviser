Three ways to run it

Daily — no Docker

Two processes, in-process cache, plain HTTP. This is a complete system, not a degraded mode. Use it for development.

Production-shaped

nginx + 3 workers + Redis over HTTPS. Use it to check behaviour under concurrency, or to reach the app from your phone.

+ Observability

Adds Elasticsearch, Kibana and Filebeat. ~1.7 GB extra, so it is opt-in behind a compose profile.

1 · Daily development

two terminals
# terminal 1 — API on :8000
cd backend && .venv/bin/python -m uvicorn app.main:app --port 8000

# terminal 2 — SPA on :5173, proxies /api to :8000
cd frontend && npm run dev

Open http://localhost:5173. Nothing else is required — no Docker, no Redis.

2 · Production-shaped stack

first run creates a self-signed certificate
./deploy/make-certs.sh
docker compose up --build -d
docker compose ps

Open https://localhost. The browser will warn about the self-signed certificate — that is expected; swap in real certs for anything beyond your own machine.

3 · With the observability tier

adds elasticsearch, kibana, filebeat
docker compose --profile observability up -d

# Kibana — the data view and saved search are created automatically
open http://localhost:5601/app/discover#/view/adviser-requests

Evaluation suites

from backend/ — the adversarial suite needs no model and no network
.venv/bin/python eval_gold.py --adversarial   # 12 guardrail fixtures, <1s
.venv/bin/python eval_gold.py --no-judge      # + tagging accuracy
.venv/bin/python eval_gold.py                 # + LLM judge on the prose

When it misbehaves

Troubleshooting

Every entry below is something that actually happened while building this, not a hypothetical.

Kibana Discover is completely empty

no documents, no error, index full

Kibana 8 shows nothing until a data view exists, and does not create one for you. The kibana-init service now does it automatically — if you are on an older stack, or it failed, create it by hand:

curl -X POST http://localhost:5601/api/data_views/data_view \
  -H 'kbn-xsrf: true' -H 'Content-Type: application/json' \
  -d '{"data_view":{"title":"adviser-*","timeFieldName":"@timestamp"}}'

Logs stop arriving in Elasticsearch, app looks fine

filebeat: "Cannot index event (status=400): dropping event!"

A field type conflict. Elasticsearch's beats template maps service and error as objects; emitting them as bare strings makes every document fail and Filebeat drops the lot silently. Replay a real line to read the actual rejection:

docker compose logs backend --tail 20 | grep -o '{"@timestamp.*}' | tail -1 \
  | xargs -0 -I{} curl -s -XPOST 'http://localhost:9200/probe/_doc' \
      -H 'Content-Type: application/json' -d '{}'

Login returns 429 and you are locked out

HTTP 429 · "Too many failed sign-ins"

The rate limiter, doing its job — five failures per fifteen minutes, keyed by IP. Wait it out, or clear the counters:

docker compose exec redis redis-cli --scan --pattern 'adviser:v1:rl:*' \
  | xargs -r -n1 docker compose exec -T redis redis-cli unlink

Backend will not start

AuthNotConfigured · "Application startup failed. Exiting."

Deliberate. AUTH_PASSWORD is missing or is still the published example value. The error message prints the exact fix. This is the app refusing to serve on a password anyone can read in the repo.

A holding shows "no data available"

one or two rows blank while the rest are fine

Yahoo dropped those symbols from a batch — it does this under load. History is cached per symbol and missing ones are retried individually, so it usually self-heals within the 10-minute TTL. Confirm it is upstream, not the app:

curl -s localhost:8000/metrics | grep missing_from_batch

Container reports unhealthy while clearly serving

"wget: can't connect to remote host: Connection refused"

IPv6. Container /etc/hosts maps localhost to ::1 as well as 127.0.0.1, busybox wget tries IPv6 first, and nginx binds IPv4 only. Health probes are pinned to 127.0.0.1 for exactly this reason — if you add a probe, do the same.

Gold watch runs but no email arrives

emailed=False, or email_error in the run row

Usually SMTP_PASSWORD is blank. It may also be the alert limiter — six per day, 45-minute cooldown — which records why it suppressed rather than staying silent:

.venv/bin/python gold_watch_run.py --test-email
curl -s -H "Authorization: Bearer $TOKEN" localhost:8000/api/gold/runs | head -c 400

Phone cannot reach the app any more

worked yesterday, times out today

Your LAN IP changed — it is DHCP-assigned. The app binds all interfaces (host: true in vite.config.js), so only the address moved:

ipconfig getifaddr en0
